# Методика нагрузочного тестирования

## Состав эксперимента

Пять каталогов соответствуют методам статьи и сравнивают базовую конфигурацию Rust-сервера с вариантом, где включён исследуемый механизм. В `benchmarks/06_integrated` оценивается сервер со всеми пятью методами против Granian. Каждый `comparison.json` хранит команды, параметры и профиль запросов; запуск записывает раунды, сводки, ошибки и метаданные в `results.json`.

Названия методов сохранены по статье:

1. `Механизм наследования ресурсов (Shared Listener Inheritance)`
2. `Механизм приёма унаследованных ресурсов (Worker Inheritance)`
3. `Внедрение пула рабочих потоков (Execution Pool)`
4. `Селективное управление телом запроса и Zero-copy буферы`
5. `Изоляция сетевой среды выполнения (Runtime Isolation)`

Тесты используют разные профили нагрузки, подходящие цели каждого метода. Shared Listener Inheritance и Execution Pool оставлены на коротком CRUD-подобном POST-сценарии. Zero-copy получает большие тела. Runtime Isolation получает смесь быстрых и задержанных запросов. Интеграционный сценарий объединяет оба типа тяжёлой нагрузки.

## Тестовое Django-приложение

Используется небольшое Django WSGI-приложение из `django_test_app`. `config.settings_perf` отключает `DEBUG`, middleware, приложения, шаблоны и базу данных, чтобы сосредоточить замер на тракте HTTP → WSGI → Django.

Исходный маршрут `GET /rps_plain` возвращает `ok`; его обработчик оставлен без изменений. Добавлен `GET /rps_heavy`, который ждёт 25 мс через `time.sleep` и возвращает короткий ответ. Маршрут принимает и POST: он полностью читает тело, затем ждёт заданную задержку и возвращает только `ok` с размером тела в заголовке. Параметр `delay_ms` позволяет выставить задержку 0 для изолированного теста буфера; по умолчанию задержка равна 25 мс.

В базовом POST-сценарии `/post` view отражает в JSON метод, путь, заголовки и тело запроса. Это CRUD-подобная проверка передачи данных, но она не сохраняет записи и не обращается к БД. Остальные маршруты (`/get`, `/put`, `/patch`, `/delete`, `/head`, `/options`, `/methods`) проверяют HTTP-методы отдельным smoke-скриптом и не участвуют во всех нагрузочных профилях.

Для 10-MiB payload в `config.settings_perf` задан `DATA_UPLOAD_MAX_MEMORY_SIZE = 12 MiB`; Rust-профили, принимающие большие тела, запускаются с `--max-body-bytes 12582912`. Так Django и Rust принимают все заявленные 10 485 760 байт, сохраняя предел выше размера тестового тела.

## Профили шести сравнений

| Каталог | Нагрузка | Сравниваемые варианты |
| --- | --- | --- |
| `01_shared_listener_inheritance` | POST `/post`, тело 1 KiB | два worker с `reuseport` против двух worker с общим слушающим FD от master |
| `02_worker_inheritance` | POST `/post`, тело 1 KiB; плюс тест старта | worker сам делает `bind` против worker, который принимает унаследованный FD |
| `03_execution_pool` | POST `/post`, тело 1 KiB | системный поток на каждый запрос (`spawn`) против постоянного Python thread pool с очередью 256 |
| `04_zero_copy` | каждый запрос — POST `/rps_heavy?delay_ms=0`, тело 10 MiB | обычный сбор фрагментов против компактного заранее выделенного буфера |
| `05_runtime_isolation` | 70% GET `/rps_plain`, 30% GET `/rps_heavy` с задержкой 25 мс | inline Python на Tokio против `spawn_blocking` в blocking pool Tokio |
| `06_integrated` | 70% быстрых GET; 20% GET `/rps_heavy`; 10% POST `/rps_heavy` с телом 10 MiB. Оба вида тяжёлых запросов задерживаются на 25 мс | kubstu со всеми пятью методами против Granian |

В интеграционном сценарии 30% запросов относятся к тяжёлой нагрузке: 20 процентных пунктов — задержанный GET и 10 — большой POST с задержкой. Ответы короткие, поэтому измерение не превращается в тест отдачи 10-MiB ответов.

Метод Zero-copy в статье — название исследуемого подхода. В текущей реализации вариант `compact_body_buffer` теперь заранее выделяет `BytesMut` по Content-Length и последовательно записывает в него входящие фрагменты. Это убирает промежуточный список и дополнительную сборку тела. При создании Python `bytes` тело всё ещё копируется, поэтому речь идёт о сокращении копирований в Rust, а не о полном zero-copy между Rust и Python.

В тесте Shared Listener Inheritance базой служит `SO_REUSEPORT`: иначе два процесса не смогли бы одновременно слушать один адрес обычным `bind`. В Worker Inheritance работает один worker в обеих конфигурациях; отличается только прямое создание сокета или получение FD от родительского процесса. Это позволяет измерять запуск и приём сокета без изменения числа worker.

## Время старта

Worker Inheritance и интеграционный тест дополнительно измеряют 40 холодных запусков каждого варианта. Запуски чередуются: в нечётном цикле сначала базовый вариант, в чётном — второй. Время считается от вызова запуска процесса до первого успешного HTTP 2xx от `/rps_plain`; сервер останавливается после ответа перед следующей попыткой.

В `results.json` поле `startup_measurement` содержит время каждой пробы, медиану, среднее, стандартное отклонение, минимум, максимум и парное сравнение. Для Worker Inheritance измеряется прямой `bind` против приёма унаследованного FD. Для интеграционного теста отдельно сопоставляются kubstu со всеми методами и Granian.

## Параметры нагрузочных прогонов

- Rust-сервер собирается в release-режиме при каждом запуске папочного `run.sh`.
- Генератор — `wrk 4.2.0`, 4 потока; 2 разминочных раунда и 10 пар измерений по 5 секунд; порядок серверов чередуется, пауза между замерами — 1 секунда.
- Для сценариев 01, 02, 03 и 05 используются 64 соединения. Для 04 и 06 — 16 соединений: пробы с телом 10 MiB при 64 соединениях вызывали ошибки записи у самого `wrk`; на 16 соединениях большие тела проходят без ошибок, а конкурентность одинакова у обеих сравниваемых конфигураций.
- Профиль — WSGI по HTTP/1.1 на `127.0.0.1`. Django и Rust-серверы обслуживают один и тот же endpoint и payload внутри каждого сравнения.
- Интеграционный Granian использует WSGI, HTTP/1, 2 worker, 2 runtime thread и 2 blocking thread. Это лучший проверенный в имеющихся профилях Granian, но не доказанный глобальный максимум.

Запуск всех серий из корня репозитория:

```sh
benchmarks/01_shared_listener_inheritance/run.sh
benchmarks/02_worker_inheritance/run.sh
benchmarks/03_execution_pool/run.sh
benchmarks/04_zero_copy/run.sh
benchmarks/05_runtime_isolation/run.sh
benchmarks/06_integrated/run.sh
```

Требуются `.venv` с Django и Granian, Rust/Cargo и `wrk` в `PATH`. Сборка задаёт `PYO3_PYTHON="$PWD/.venv/bin/python"`. Настройки циклов можно менять аргументами `run.sh`; для 10-MiB сценариев рекомендуется сохранять 16 соединений.

В `results.json` `mean_rps` — среднее RPS по раундам, `stdev_rps` — выборочное стандартное отклонение. `median_p95_ms` и `median_p99_ms` — медианы перцентилей wrk по раундам. Скрипт также сохраняет парные разницы RPS и их 95%-й интервал. p95 и p99 — перцентили задержки запроса, а не доверительные интервалы.

## Результаты прогонов

Shared Listener Inheritance и Execution Pool были выполнены 29.09.2026 на коротком POST с телом 1 KiB. Worker Inheritance повторён 30.09.2026 на том же запросе и дополнен тестом времени старта. Zero-copy, Runtime Isolation и интеграционный профиль выполнены 30.09.2026 с целевой нагрузкой каждого метода. Во всех завершённых сериях зарегистрировано 0 ошибок HTTP и сокетов.

| Сравнение | RPS: базовый → вариант | p95, мс: базовый → вариант | p99, мс: базовый → вариант | Парная разница RPS, 95% ДИ |
| --- | ---: | ---: | ---: | ---: |
| Shared Listener Inheritance | 12 352,52 → 19 792,47 | 9,464 → 6,288 | 12,148 → 7,582 | +6 931…+7 949 |
| Worker Inheritance | 12 450,84 → 12 236,34 | 9,221 → 9,409 | 11,749 → 11,981 | −430…+1 |
| Execution Pool | 10 219,24 → 12 423,76 | 11,612 → 6,020 | 17,748 → 10,032 | +2 090…+2 319 |
| Zero-copy, тело 10 MiB | 265,94 → 287,51 | 74,258 → 70,737 | 82,652 → 80,741 | +7,86…+35,28 |
| Runtime Isolation, нагрузка 70/30 | 225,15 → 7 294,63 | 437,588 → 29,612 | 489,923 → 30,488 | +7 044,60…+7 094,36 |
| Интеграция kubstu → Granian | 453,93 → 434,71 | 83,065 → 86,845 | 96,041 → 101,401 | −20,58…−17,86 |

В Worker Inheritance медиана старта составила 146,15 мс для прямого `bind` (SD 102,82 мс; диапазон 116,91–792,89 мс) и 129,18 мс для приёма FD (SD 4,80 мс; диапазон 122,88–143,13 мс). Парная медиана разницы «приём FD минус прямой старт» — −17,15 мс; в baseline есть единичный старт 792,89 мс, который сильно увеличивает разброс.

В интеграционном сравнении медиана старта kubstu — 149,18 мс (SD 21,44; 138,85–280,84 мс), Granian — 278,59 мс (SD 14,17; 267,50–353,74 мс). Парная медиана разницы «Granian минус kubstu» — +131,22 мс.

Новый Zero-copy тест показал прирост RPS примерно на 8,1%; парный интервал выше нуля. Runtime Isolation резко улучшил метрики на смешанной нагрузке, потому что inline sleep блокировал потоки Tokio. Интеграционная серия с 10-MiB запросами показала преимущество kubstu примерно на 4,2% по среднему RPS и меньшие медианы p95/p99. Эти результаты относятся к данному синтетическому маршруту и конкретным настройкам.

Полные раунды, версии, команды и старты находятся в JSON-файлах каждой папки `benchmarks/01_.../results.json` — `benchmarks/06_integrated/results.json`.

## Стенд и версии

- MacBook Air `MacBookAir10,1`, Apple M1;
- 8 ГБ оперативной памяти, 8 логических CPU (M1: 4 производительных и 4 энергоэффективных ядра);
- macOS 26.6.2, Darwin 25.6.0, архитектура `arm64`;
- Rust `1.98.1`, Python `3.14.3`, Django `6.0.8`, Granian `2.8.3`, `wrk 4.2.0`;
- сетевые зависимости Rust зафиксированы в `Cargo.lock` (в том числе Hyper, Tokio и PyO3).

В статье и более ранних файлах использовались Python 3.12.0 и Django 6.0.3, поэтому прежние измерения нельзя смешивать с этой серией. Каждый новый `results.json` фиксирует фактические версии Python, Django, Granian, Rust и параметры `wrk`.

## Ограничения

Приложение не выполняет SQL-запросы и не эмулирует полную CRUD-систему с постоянным хранением. Измеряется серверный тракт на коротких ответах, 10-MiB входящих тел или синтетической задержке 25 мс. Тест не прогнозирует работу с реальной базой данных, большими ответами и внешними сервисами. Текущий скрипт не собирает CPU и RSS; эти поля нельзя восстановить из RPS и задержек. Фоновая нагрузка и тепловой режим macOS также влияют на повторные запуски.
