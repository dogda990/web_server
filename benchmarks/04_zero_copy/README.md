# Селективное управление телом запроса и Zero-copy буферы

Изолированный AB-тест сравнивает сервер с отключённым и включённым компактным буфером. Каждый запрос — `POST /rps_heavy?delay_ms=0` с телом 10 MiB; view читает его целиком, возвращает короткий ответ и не добавляет искусственную задержку. В `settings_perf` лимит Django поднят до 12 MiB, а Rust принимает тела до 12 MiB.

Запуск из корня репозитория:

```sh
benchmarks/04_zero_copy/run.sh
```

Скрипт чередует порядок серверов, выполняет 2 прогревочных раунда на вариант и 10 пар измерений по 5 секунд, использует 4 потока wrk и 16 соединений. Для больших тел меньшее число соединений снижает вероятность ошибок записи генератора и одновременно удерживает одинаковую конкурентность у обеих конфигураций. Выводит RPS, p95 и p99; сохраняет сырые раунды и сведения о среде в `results.json`.

Изменяемый параметр описан в `comparison.json`. Режим `compact_body_buffer` заранее выделяет один буфер по Content-Length и последовательно добавляет в него пришедшие фрагменты, избегая промежуточного списка и последующей сборки. Создание Python `bytes` всё ещё копирует тело, поэтому тест оценивает сокращение копирований и накладных расходов в Rust, а не полную передачу zero-copy.

Прогон 30.09.2026: базовый вариант — 265,94 RPS, p95 74,258 мс, p99 82,652 мс; компактный буфер — 287,51 RPS, p95 70,737 мс, p99 80,741 мс. Парная разница RPS +21,57 (95%-й интервал +7,86…+35,28). Ошибок не было.
